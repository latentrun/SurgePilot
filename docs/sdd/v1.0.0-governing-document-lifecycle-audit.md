## 1. Audit rule

Lifecycle state and release-baseline membership are independent:

- `Draft`, `Accepted`, and `Superseded` describe whether a live document currently authorizes
  implementation.
- The immutable `v1.0.0` tag records the exact historical document and code snapshot shipped as the
  first public baseline.
- Presence in the tag proves that a document was baseline evidence; it does not mean every roadmap,
  future-stage, non-goal, or inactive capability described inside it was implemented.
- Status-field edits do not grant approval. An explicit user decision or accepted governance
  mechanism must exist first.

The tag is the frozen historical record. Live documents may evolve through accepted changes without
rewriting what the tag contained.

## 6. Baseline exclusions

The following are excluded from release-baseline behavior unless independently demonstrated by an
accepted source and the tagged implementation:

- Future or inactive material in the PRD, Foundation SDDs, Slice indexes, or roadmap prose.
- Placeholder Slices and proposed plans.
- A navigation label, route stub, enum value, schema extension point, or partial implementation that
  is not activated by an accepted Slice/ADR.
- Capabilities explicitly listed as non-goals or forbidden expansions in an accepted source.
- Changes made after `37cc8e4a16590f3c67403312b680a64309e61637`.

## 7. Findings

1. The immutable tag already provides the correct frozen historical snapshot. Live governance does
   not need a second `Frozen` lifecycle state.
2. PRD, Foundation SDD, and P0 Slice status labels contain legacy Draft wording even though their
   implemented portions formed the released baseline. Bulk replacement would blur mixed future
   content and falsely create approval, so this audit leaves those fields unchanged.
3. Accepted ADRs and accepted/active Slice SDDs remain the explicit approval sources for their
   bounded capabilities.
4. Current task discovery must use the live SDD entry and P1/P2 indexes. The v1.0.0 tag is evidence,
   not the current scope registry.

## 8. Change protocol

- Update a live PRD/SDD/ADR through the normal accepted design process; never edit metadata merely
  to make implementation appear authorized.
- Use Git history and immutable tags to inspect earlier baselines.
- When a later release needs a release-specific audit, create a new audit anchored to that tag; do
  not rewrite this v1.0.0 record.
- Record a discovered design/implementation mismatch as an explicit follow-up. Do not silently
  declare either side authoritative solely to complete a lifecycle audit.
